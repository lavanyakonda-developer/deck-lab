  Phase 1 — Slide Schema & Deck State Model

  Objective: Design the structured slide schema and the client-side state model that everything else (AI and manual) will mutate.
  Requirements covered: M5 (schema), foundation for M2, M3, M7.
  Features: A Deck = ordered Slide[]; Slide has id, type (title, content, two-column, comparison, bullets, table, image, chart, section…), title, body
  (discriminated union: bullets / paragraphs / table / image ref / chart spec), layout hints (alignment, columns), speakerNotes. Renderer components per
  slide type, driven purely by this schema. A seeded sample deck to test rendering without AI.
  Technical work: Zod schemas in lib/schema/slide.ts, Zustand deck store (store/deckStore.ts) with slides, selectedSlideId, pure reducer-style actions
  (addSlide, updateSlide, deleteSlide, reorderSlides, changeLayout) — same action names the AI tools will call later, so both paths converge on one store.
  Files/components: lib/schema/slide.ts, store/deckStore.ts, components/deck/slides/{TitleSlide,ContentSlide,TwoColumnSlide,ComparisonSlide,TableSlide}.tsx.
  Dependencies: Phase 0.
  Manual testing checklist:
  - Seed deck renders correctly for every slide type.
  - Calling store actions from a dev/test button updates the canvas instantly.
    Automated verification: Zod schema unit tests (valid/invalid slide payloads); store action unit tests.
    Definition of Done: Any slide shape in the schema renders correctly from static/seeded data, and store actions correctly mutate state.

  Phase 3 — AI Initial Generation ("Phase 1" of Two-Phase Generation)

  Objective: Prompt → first-draft multi-slide deck via OpenAI structured output. This is explicitly the bulk generation half of the "two-phase generation"
  requirement (M8).
  Requirements covered: M1 (chat UI, generation direction only), M4, M5 (schema enforced round-trip), M8 (phase 1), M12.
  Features: Chat input accepts a prompt ("Create a 5-slide deck on our Q3 roadmap"); server route calls OpenAI with the Zod→JSON-schema deck schema as a
  Structured Output; response replaces/populates the deck store; chat shows the assistant's message.
  Technical work: app/api/generate/route.ts (server-only, reads OPENAI_API_KEY), OpenAI Structured Outputs call constrained to the deck schema, Zod-validate
  the response before writing to the store, basic chat message list + input component, loading state.
  Files/components: app/api/generate/route.ts, lib/ai/openaiClient.ts, components/chat/ChatPanel.tsx (wired), store/chatStore.ts.
  Dependencies: Phase 1 (schema), Phase 2 (store/UI to populate).
  Manual testing checklist:

  - Prompt "Create a 5-slide deck on X" produces 5 coherent, on-topic slides in the editor.
  - Malformed/empty prompt handled gracefully (no crash).
  - Confirm OPENAI_API_KEY never appears in client bundle/network tab (only the /api/generate call is visible).
    Automated verification: Route handler test with a mocked OpenAI response validating Zod parsing/error paths.
    Definition of Done: A real prompt produces a real, schema-valid, multi-slide deck rendered live in the editor — no mocked data.

  Phase 4 — Agentic Tool-Use & Diff-Based Refinement ("Phase 2" of Two-Phase Generation)

  Objective: Conversational refinement via function calling, applying targeted patches instead of regenerating the deck.
  Requirements covered: M1 (full), M6, M7, M8 (phase 2) — the heart of the "agentic system" requirement.
  Features: User says "Make slide 3 more concise" / "Add a pricing slide before the conclusion" / "Turn slide 2's bullets into a table" → model receives
  current deck context (compact summary: slide ids, types, titles, short content) + tools add_slide, update_slide, delete_slide, reorder_slides,
  change_layout → model calls the appropriate tool(s) with only the changed fields → store applies the patch → canvas updates. Manual edits made between AI
  turns are preserved because both paths write to the same store via the same action set (proven in Phase 1/2).
  Technical work: app/api/chat/route.ts running an OpenAI tool-calling loop, tool definitions in lib/ai/tools.ts (Zod-validated args mapped 1:1 to store
  actions), deck-context serializer (lib/ai/deckContext.ts) sent as system/context message, tool-call results applied via existing store actions (not a new
  code path).
  Files/components: app/api/chat/route.ts, lib/ai/tools.ts, lib/ai/deckContext.ts, components/chat/ChatPanel.tsx (tool-call activity indicator, e.g.
  "Updating slide 3…").
  Dependencies: Phase 3.
  Manual testing checklist:
  - "Make slide 3 more concise" only changes slide 3; other slides byte-identical.
  - Manually edit slide 1, then ask AI to change slide 4 — manual edit on slide 1 survives.
  - "Add a slide about pricing before the conclusion" inserts at the correct position via add_slide+reorder_slides, not a full rebuild.
  - "Rewrite slide 2's bullets as a comparison table" changes layout/type via change_layout/update_slide.
  - Ask for something ambiguous — verify the model asks or makes a reasonable single-tool choice rather than nuking the deck.
    Automated verification: Unit tests per tool (args → correct store mutation), integration test simulating a tool-call response and asserting only the
    targeted slide changed.
    Definition of Done: Chat-driven edits are demonstrably surgical (diffable before/after state), and manual + AI edits coexist without data loss.

  Phase 5 — Streaming

  Objective: Replace spinner-then-dump with incremental, visible progress for both initial generation and refinement.
  Requirements covered: M10.
  Features: During initial generation, slides appear on the canvas/thumbnail rail one at a time as they're produced. During chat refinement, the assistant's
  textual reasoning/response streams token-by-token, and tool-call effects apply as soon as each tool call completes.
  Technical work: Switch /api/generate and /api/chat to OpenAI streaming mode, parse partial structured-output/tool-call chunks server-side (buffer until
  one slide/tool-call is complete, then emit an SSE/stream event to the client), client-side stream reader updates store incrementally.
  Files/components: app/api/generate/route.ts, app/api/chat/route.ts (streaming), lib/ai/streamParser.ts, components/chat/ChatPanel.tsx (streaming text
  render), store actions callable incrementally.
  Dependencies: Phase 3, Phase 4.
  Manual testing checklist:
  - Generating a 6+ slide deck visibly populates the thumbnail rail slide-by-slide, not all at once.
  - Chat responses stream visibly (text appears progressively).
  - Network interruption mid-stream doesn't corrupt store state (partial slide isn't committed half-written).
    Automated verification: Stream parser unit tests with chunked mock input reconstructing correct slide objects.
    Definition of Done: Both generation and refinement are visibly incremental in the UI.

  Phase 6 — Rich Content: Images, Charts, Tables

  Objective: AI can produce and the editor can render non-text slide content.
  Requirements covered: M11.
  Features: image slide/body type (AI-generated via image API, with a placeholder fallback if generation fails/is skipped), chart type (AI proposes chart
  kind + data, rendered with Recharts), table type completed end-to-end (AI can generate and edit tables, already schema-supported since Phase 1).
  Technical work: app/api/generate-image/route.ts (server-side OpenAI image call), chart data schema + ChartSlide.tsx (Recharts), extend
  update_slide/add_slide tool args to accept chart/table/image payloads, extend deck-context serializer to summarize non-text content compactly (avoid
  bloating token usage with base64 images).
  Files/components: components/deck/slides/{ChartSlide,ImageSlide,TableSlide}.tsx, app/api/generate-image/route.ts, lib/ai/tools.ts (extended).
  Dependencies: Phase 4 (tools), Phase 1 (schema already anticipates these types).
  Manual testing checklist:
  - "Add a chart slide showing our Q1-Q4 revenue growth" produces a rendered chart with sensible data.
  - "Add an image of a modern office to slide 2" produces/attaches an image, with a visible fallback if generation is unavailable.
  - Table generation/editing (add row, edit cell) via both chat and manual click.
    Automated verification: Chart data schema validation tests; image route test with mocked failure → verifies fallback path, not a crash.
    Definition of Done: All three rich content types can be created by the AI and are visible/editable in the deck.

  Phase 8 — Unified Undo/Redo (Nice to Have)

  Objective: One history stack covering both AI tool-calls and manual edits.
  Requirements covered: N2.
  Features: Undo/redo buttons (and keyboard shortcuts) step through a single chronological history regardless of edit source.
  Technical work: Command-pattern wrapper around all store actions (each mutation pushes an inverse op onto an undo stack), integrate into both the
  manual-edit call sites and the AI tool-execution path from Phase 4 — no new mutation path, only wrapping the existing one.
  Files/components: store/historyMiddleware.ts, components/toolbar/UndoRedo.tsx.
  Dependencies: Phase 4 (all mutation paths must exist and converge first).
  Manual testing checklist:
  - Manual edit → undo restores prior text.
  - AI adds a slide → undo removes it; redo brings it back.
  - Interleaved manual + AI actions undo in correct chronological order.
    Automated verification: History middleware unit tests (push/undo/redo sequences, branching after undo).
    Definition of Done: Undo/redo correctly reverses any mix of manual and AI actions in true chronological order.

  Phase 10 — Context Window Management (Nice to Have)

  Objective: Keep chat + deck context sent to the LLM bounded as the conversation grows.
  Requirements covered: N3.
  Features: Long chat histories get summarized/truncated before being sent; deck context sent to the model stays a compact summary (already true from Phase
  4) rather than the full slide JSON, with size scaling handled explicitly as slide count grows.
  Technical work: Token counting (tiktoken or provider utility), rolling summarization of older chat turns via a cheap summarization call or simple
  truncation-with-marker strategy, cap on deck-context size (e.g., summarize slide bodies beyond N slides).
  Files/components: lib/ai/contextManager.ts, wired into app/api/chat/route.ts.
  Dependencies: Phase 4 (deck context serializer to extend), Phase 5 (streaming already in place).
  Manual testing checklist: Simulate a long chat (20+ turns) and a large deck (15+ slides); confirm requests don't error on token limits and refinement
  quality doesn't collapse.
  Automated verification: Unit test asserting context payload stays under a token budget for synthetic large inputs.
  Definition of Done: The app remains functional and responsive on long sessions/large decks without hitting context-length errors.
